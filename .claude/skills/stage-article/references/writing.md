# 写作范式

目标读者有两类：一年后回来复习的作者本人，和第一次读到的同行。两者都希望「读完就懂、以后能用」。

## 结构

推荐骨架（按内容取舍，不必每节都有）：

| 章节 | 作用 | 常用写法 |
|---|---|---|
| TL;DR | 一句话结论 | `::: tldr` |
| 出处段 | 来源、链接、本文加了什么 | 普通段落 |
| 问题 | 为什么难；现有办法为什么不行 | 时间码章节 + 段落 |
| 尝试与失败 | 走过的弯路——往往是最有价值的部分 | `attempt-log` 组件 |
| 化简 | 把大问题压成一个可检验的小问题 | `::: quote` |
| 方案 | 怎么做，关键机制 | 交互组件 + 段落 |
| 验证 | 怎么知道它对 | 段落 / 组件 |
| 结果与局限 | 适用范围、成本、不能做什么 | `::: ledger` |
| 方法论 | 3–5 条能迁移到别处的原则 | `::: lessons` |
| 参考 | 原始出处 | `## [REF] 参考` + 列表 |

范例里每一节都对应了视频的一个阶段：`content/docs/ai-rig-any-monster/index.md`。

## 语气

- 中文，平实，像给一位聪明但不了解背景的同事讲。少用形容词，多用具体的数和例子。
- 每段只讲一件事，第一句就是这段的结论。
- **加粗**只给真正的关键词，一段最多一两处——页面上加粗会画荧光划线，多了就没有重点了。
- 引用原话时用自己的话重述大意；需要原话就只引短句并注明出处。
- 不写「本文将介绍」「众所周知」这类空话。

## 标题、摘要与 frontmatter

- `title`：完整、可检索，可以带副标题（「让 AI 给任何怪物做骨骼动画：双机位视频 + 专属关节识别器」）。
- `display_title`：首屏大字，短，方括号里的词荧光高亮（「让 AI 给[任何怪物]做骨骼动画」）。不要以 `[` 开头（会被当成列表），需要时整体加双引号。
- `summary`：一两句，讲清「什么问题 + 什么解法」。它同时是首屏导语、列表摘要、RSS 和 CSDN 摘要。
- `kicker`：首屏小字分类，例如「技术文档 / 3D · 计算机视觉」。
- `source` + `source_label`：出处链接与简称，首屏显示为 `SRC · 简称`。
- `slug` 用英文（文件夹名即 URL），CSDN 回链和分享时更干净。

## 章节标题

- 视频类：`## [01:20] 标题`，时间码取视频章节或字幕时间，方便读者对照原片。
- 非视频：用短标签 `[NOTE]`、`[RESULT]`、`[REF]`，或不写方括号（自动编号 §NN）。
- 标题写成观点，而不是名词：「一张图里，放两台相机」好过「双机位方案」。

## 选择交互概念

问自己：读者动一下手，会不会比读三段文字更快懂？

适合：
- 几何 / 空间关系（三角测量、投影、坐标变换）；
- 流程与数据流（流水线、生成过程的每一步）；
- 对比与取舍（A 方法 vs B 方法的结果）；
- 「如果去掉这一步会怎样」（开关式演示）；
- 质量保证 / 判定过程（打分、考试、阈值）。

不适合：纯观点、纯引用、本来就很短的列表。

每篇 3–5 个组件就够了。组件太多会打断阅读节奏，每个都应该对应一个「豁然开朗」的时刻。

## 「示意」的边界

- 原文给的数字（4 天、3000 张、30 分钟、4/10）可以直接写进文字和组件。
- 原文没给、但为了画图必须有的数字（误差厘米数、合格线、哪几帧对错），只能出现在组件里，并在组件下方用 `w-caption` 写明「示意」。
- 文末参考区再说明一次：「标注『示意』的数值和图形为图解，不是原文公布的数据。」
