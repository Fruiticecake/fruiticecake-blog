让机器人或端侧大模型助手快速对准唤醒来源，靠的不是把麦克风音频持续传给云端大模型，也不是唤醒后让摄像头原地盲扫，而是一条**端侧快环**：用独立线程读 **ALSA PCM** 音频防 **XRUN** 丢字 → **VAD** 每 20 ms 拦掉静音与环境噪声 → 离线 **KWS** 只盯预设唤醒词 → 多麦克风阵列用 **TDOA / GCC-PHAT** 从几十到几百微秒的时间差里反推声源方位角 **DOA** → 舵机直接转头对准，再交给视觉微调。
:::

做桌面机器人、智能机械臂或具身智能助手时，最先暴露交互延迟和「智障感」的往往不是大模型推理，而是最开始的 300 毫秒：人在旁边喊了一声唤醒词，设备要么半天没反应，要么像监控探头一样左右缓慢扫描找人，要么在空调底噪里自己莫名其妙醒过来。

本文把「听见唤醒词」到「瞬间转头对准说话人」这条语音前端链路拆开讲透，覆盖五个绕不开的工程概念：**KWS**、**VAD**、**DOA**、**TDOA / GCC-PHAT** 与 **PCM / ALSA / XRUN**。文中的字节率、角度分辨率、混响误差与环形缓冲溢出数据均由文章目录下 `code/verify_doa.py`（纯 Python 标准库，零外部依赖）实测算出。

## [PROB] 为什么机器人不能盲扫，也不能把声音全丢给大模型

一个常见的直觉方案是「大模型什么都能理解，直接把麦克风连到云端 ASR + 大模型，或者唤醒后让云台带着摄像头转一圈跑 YOLO 找人」。这两条路在真实硬件上都会立刻撞墙。

第一，**24 小时全时上传音频流做云端识别不可行**。哪怕只算单声道 `16 kHz / 16-bit` 原始 PCM，每秒也要产生 `31.25 KiB`（每小时超过 100 MB）；更致命的是延迟、带宽费用、断网不可用以及客厅/卧室的隐私红线。设备必须能在本地完全离线、低功耗地长年监听，只有确认「你在叫我」那一瞬间，才去唤醒后面的 ASR 和大模型。

第二，**唤醒后靠视觉盲扫找人太慢，而且缺乏「生命感」**。普通广角或腕部摄像头视场角有限，如果说话人在机器人侧后方，机械臂必须先转轴扫描、逐帧跑目标检测，动辄 1.5 到 3 秒才能锁定目标；万一房间里不止一个人，单靠视觉还不知道**究竟是谁喊了它**。

::: quote
把「听懂你在叫我」和「知道你在哪边」压进同一个端侧快环：*KWS 解决要不要醒，DOA 解决往哪边转*。
:::

## [PIPE] 一条从声波到转头的五段快环流水线

把大问题拆小之后，机器人端侧语音前端的标准流水线非常干净：前端全在本地跑，输出给运动控制层和决策层的只是一个极轻的事件结构（触发了哪个词、置信度多少、声源水平角几度、角度是否有效）。

::: interactive pipeline title="语音唤醒到转头对准的五段快环" hint="CLICK / ← →" note="点击或用方向键切换每一步；前四步全部跑在本地端侧，不依赖网络。"
1. **PCM / ALSA 采集**（独立音频线程）：按每拍 20 ms（320 frames @ 16 kHz）从声卡环形缓冲拉取原始未压缩音频，与视觉和 NPU 推理线程彻底隔离，避免 XRUN 丢字。→ 连续多通道 PCM 流
2. **VAD 语音活动检测**（Silero VAD）：站在 KWS 前面的门卫，每 20 ms 判断当前帧是不是人声，把静音、风扇声和空调白噪声直接丢弃。→ 人声活跃窗口（带前后缓冲）
3. **KWS 关键词检出**（Sherpa-ONNX Zipformer）：极轻量的本地离线小模型，只在 VAD 放行后盯着音频流里是否出现预设固定词（如「小智同学」「停下」「关灯」）。→ 唤醒事件 + 冷却防抖
4. **DOA 声源定位**（多麦阵列 TDOA / GCC-PHAT）：利用声音到达不同麦克风的微秒级时间差，算出说话人相对设备的水平方位角 θ（例如 -35° 表示在左侧）。→ 声源方位角（度）
5. **快环响应与视觉精调**（运动控制 + 视觉）：机械臂立刻按方位角转头并播报回应，进入说话人视野后再用轻量视觉模型完成精细对准，同时异步把后续语句交给 ASR 与大模型。→ 300 ms 级自然对视
:::

这条链路把**快环**（离线、确定性、< 300 ms 转头回应）和**慢环**（云端或端侧大模型深度理解、多步任务规划）切开了。即使家里断网，你喊「停下」或「关灯」，机器人依然能在本地立刻响应。

## [VAD] VAD 是门卫，KWS 才是只认暗号的哨兵

初学者最容易把 **VAD**、**KWS** 和 **ASR** 混为一谈。三者在能力边界和算力开销上完全不在一个量级：

| 模块 | 英文全称 | 它回答什么问题 | 典型算力与联网需求 |
|---|---|---|---|
| **VAD** | Voice Activity Detection（语音活动检测） | 这 20 ms 里有没有人说话？ | 极低（如 Silero VAD 单帧 CPU < 0.5 ms），纯本地离线 |
| **KWS** | Keyword Spotting（关键词检出） | 刚才那段人声里有没有预设的几个固定词？ | 很低（端侧小核占用通常 < 12% CPU，内存 < 60 MiB），纯本地离线 |
| **ASR** | Automatic Speech Recognition（自动语音识别） | 这句话完整说了什么文字？ | 较高（需大词汇量声学/语言模型），可端侧异步跑或上云 |

**KWS 为什么不能省掉前面的 VAD？** 房间里 90% 以上的时间并没有人说话，只有空调低频噪声、机箱风扇、键盘敲击或窗外车流。如果把全天 24 小时的 PCM 帧不加过滤地持续灌进 KWS 模型，会立刻带来两个问题：一是端侧芯片的小核长期空转发热；二是某些稳态噪声或瞬态敲击在声学特征空间里偶尔会撞到唤醒词模板，把**误唤醒率**（False Accept Rate）拉高一个数量级。

**工程里还有一个容易踩的细节：Hangover（拖尾窗口）与前置缓存。** VAD 判定人声开始的瞬间，第一个字的起音（比如「小」的声母）可能刚好落在前 1 到 2 帧；判定人声结束时，字与字之间的短暂停顿也可能让概率短暂跌破阈值。所以工程上通常会在 VAD 之前挂一个 `200~300 ms` 的短环形预缓冲（Pre-roll），并在 VAD 跌落后再多放行 `300 ms` 的 Hangover 拖尾，确保喂给 KWS 的唤醒词首尾完整。

::: interactive vad-kws-gate title="VAD 门卫怎么拦住噪声、只放行真正的唤醒词" hint="SWITCH / TOGGLE" note="切换不同环境声音，并开关「启用 VAD 门卫」，观察 KWS 的实际调用次数与风险。"
| 声音片段 | 典型特征 | 裸跑 KWS（无 VAD） | 启用 VAD 门卫后 |
|---|---|---|---|
| 空调白噪声 | 持续宽频低噪，人声概率约 0.05 | KWS 每 20 ms 持续推理，白白耗电且偶发误唤醒 | VAD 直接丢弃，KWS 零调用 |
| 键盘敲击 | 瞬态脉冲尖峰，人声概率约 0.12 | 瞬态频谱易扰动流式状态，增加误触发风险 | 低于人声阈值直接拦截，KWS 休眠 |
| 旁人闲聊 | 真实人声，概率约 0.88，不含唤醒词 | KWS 持续匹配但分数未过阈，不触发 | VAD 放行给 KWS，KWS 识别非预设词后静默丢弃 |
| 喊出「小智同学」 | 真实人声，概率约 0.96，命中词表 | 触发唤醒（但平时一直在空跑） | VAD 放行 + 预缓冲补齐字头，KWS 命中触发唤醒并进入 1500 ms 冷却 |
:::

KWS 选型上，开源离线方案里 **Sherpa-ONNX**（Zipformer 流式 KWS 搭配 Silero VAD）是目前嵌入式 C/C++ 项目里很稳的一套组合：纯 C API 方便集成、支持自定义中文词表、完全离线免费；相比之下，商业闭源引擎（如 Porcupine）虽轻但受限于授权和联网校验，而老一代的 PocketSphinx / Snowboy 在室内噪声下的漏检与误唤醒已经明显掉队。另外，命中唤醒词后必须配一段 `1000~1500 ms` 的冷却期防抖，避免流式滑窗在相邻两拍里把同一声呼唤上报两次。

## [DOA] DOA 与 TDOA：几十微秒的时间差，怎么反推出你在哪边

唤醒解决的是「叫没叫我」，**DOA**（Direction of Arrival，声源到达方向）解决的是「人在哪边」。单个麦克风只能听到声波的强弱变化，听不出方向——就像蒙住一只耳朵很难分辨声音来自左边还是右边。要算方向，至少需要**两个以上麦克风组成的阵列**。

DOA 最经典的物理基础是 **TDOA**（Time Difference of Arrival，到达时间差）。空气中声速 `c ≈ 340 m/s`（室温 20℃ 左右）。假设两个麦克风间距为 `d`，说话人距离设备远大于 `d`（满足远场平面波近似），声波与阵列法线夹角为 `θ`（约定左侧为负、右侧为正）。

此时，声波到达较远麦克风多走的路程是 `ΔL = d · sin θ`，对应的到达时间差为：

```text
Δt = (d · sin θ) / c
θ  = arcsin(c · Δt / d)
```

别小看这个初高中几何公式，把真实硬件参数代进去跑一遍（`d = 6 cm`，`c = 340 m/s`，见 `code/verify_doa.py`），马上能看到两个平时光看概念绝对意识不到的工程真相：

| 真实角度 θ | 声程差 ΔL (cm) | 时间差 Δt (us) | 16 kHz 下采样点差 | 48 kHz 下采样点差 |
|---|---|---|---|---|
| -90°（正左） | -6.00 | -176.5 | -2.82 | -8.47 |
| -60° | -5.20 | -152.8 | -2.45 | -7.34 |
| -35°（左前方） | -3.44 | -101.2 | -1.62 | -4.86 |
| 0°（正前方） | 0.00 | 0.0 | 0.00 | 0.00 |
| +35°（右前方） | +3.44 | +101.2 | +1.62 | +4.86 |
| +60° | +5.20 | +152.8 | +2.45 | +7.34 |
| +90°（正右） | +6.00 | +176.5 | +2.82 | +8.47 |

**第一个真相：时间差小到「按整数采样点根本不够分」。** 麦克风间距 6 cm 时，哪怕声音从正侧面（±90°）打过来，最大时间差也只有 `176.5 us`。而语音唤醒常用的 `16 kHz` 采样率，相邻两个采样点之间间隔就是 `62.5 us`。这意味着在正前方附近，**哪怕时间差只差 1 个整数采样点，推出来的角度就会直接跳变 `20.7°`**！如果直接拿整数滞后算角度，机器人转头永远只能一格一格地大跨度抽动。

工程上解决粗糙分辨率靠三件事配合：一是做**亚采样插值**（比如三点抛物线插值或频域补零插值），把整数采样点细化到小数点后；二是在做 DOA 的通道用更高采样率（`48 kHz` 下单采样点缩到 `20.83 us`，正前方步进降到 `6.8°`）；三是适当拉开阵列孔径或增加麦克风数量做联合最小二乘/SRP-PHAT 网格搜索。

**第二个真相：2 麦线性阵分不清「前面」还是「后面」。** 从 `sin θ` 的对称性就能看出，位于设备正前方偏右 `+35°` 的人和位于正后方偏右 `+145°` 的人，到两个麦克风的路程差完全一样，产生的 `Δt` 都是 `+101.2 us`。如果设备靠墙放（声源都在前半平面），2 麦线性阵够用；如果机器人放在房间中央或需要 360° 听声辨位，就必须上 **4 麦或 6 麦环形阵列**，用正交方向的麦克风对交叉消掉前后镜像模糊。

::: interactive tdoa-lab title="TDOA 几何实验：移动声源，看微秒级时间差与前后镜像模糊" hint="DRAG / ← → / SWITCH" note="拖动声源或按左右方向键改变角度；切换 2 麦线性阵与 4 麦环形阵，把声源转到设备后方观察镜像歧义。"
| 阵列形态 | 可覆盖范围 | -35° 时 16 kHz 采样差 | 前后镜像问题 |
|---|---|---|---|
| 2 麦线性阵（d = 6 cm） | 前半平面 -90° ~ +90° | -1.62 samples（-101.2 us） | 存在：+35° 与 +145° 产生完全相同的 Δt，无法区分前后 |
| 4 麦环形阵（r = 3.5 cm） | 360° 全向无死角 | 两组正交麦对联合求解 | 消除：前/后麦对的时间差符号相反，可唯一锁定 0°~360° 方位角 |
:::

## [PHAT] 室内全是回声和噪音，为什么普通互相关会指错方向

知道了 `Δt` 就能算角度，那问题就化简成了一件事：**怎么从两路含噪录音里准确抠出那几十到几百微秒的 `Δt`？**

最直观的办法是做**普通互相关**（Cross-Correlation，CC）：把麦克风 1 的波形左右平移 `τ`，和麦克风 2 逐点相乘求内积，找重合度最高的位置。在空旷无回声的消声室里，这招很准。

但只要搬进真实客厅或卧室，普通互相关立刻就会翻车，原因有两个：
- **语音和空调嗡嗡声的能量极度集中在低频**：低频波长很长（250 Hz 声波波长 1.36 米），波形平缓，导致互相关主峰又胖又钝，还容易被来自另一侧的空调/风扇强窄带噪声直接拉偏。
- **墙壁和桌面反射制造大量混响**：麦克风收到的不只是直达声，还混着晚到几毫秒、来自墙面反射方向的多路回声，普通互相关很容易被叠加后的伪峰带偏。

**GCC-PHAT**（Generalized Cross-Correlation with Phase Transform，广义互相关相位变换）的解法非常漂亮，核心操作只有一步——**频域白化（只留相位，扔掉幅度）**：

```text
G_PHAT(f) = ( X2(f) · conj(X1(f)) ) / ( |X2(f) · conj(X1(f))| + eps )
R_PHAT(τ) = IFFT( G_PHAT(f) )
```

为什么要除以幅度 `|X2(f) · conj(X1(f))|`？因为时间延迟 `τ` 的全部几何信息都藏在**各个频率的相位差** `exp(-j · 2π · f · τ)` 里，和每个频率声音有多大声无关。把所有频率的幅度归一化成 `1` 之后：
1. 原本嗓门震天的 250 Hz 空调嗡嗡声，在频域里不再占绝对话语权，只剩一个频点的权重；
2. 宽带人声的各个高频和低频分量以同等权重在真实延迟 `τ` 处同相叠加，把原本圆胖的主峰压缩成一根极尖的**脉冲针（Dirac-like peak）**，把混响伪峰压在脚下。

我们在 `code/verify_doa.py` 里构造了一个贴近真实室内的对照组：真实声源在 `-35.0°`（`-101.2 us`，`-1.62 samples`），叠加两组来自 `+55°` 和 `+70°` 墙面的室内回声、一路来自 `+45°` 的 250 Hz 强低频机箱/空调嗡嗡声，以及高斯白噪声。同一段 64 ms（1024 点）音频直接对比结果如下：

| 算法 | 整数峰滞后 (samples) | 整数峰估计角度 | 抛物线插值滞后 | 最终估计角度 | 相对 -35.0° 误差 |
|---|---|---|---|---|---|
| 普通互相关（CC） | 0 | +0.0° | +0.19 | +3.9° | **38.9°**（指偏到右侧） |
| **GCC-PHAT** | -2 | -45.1° | -1.71 | **-37.3°** | **2.3°** |

注意看 GCC-PHAT 这一行的两列对比：哪怕相位白化已经准确把主峰拉回真实位置附近，只取整数采样点（`-2`）依然有 `10.1°` 量化误差；加上三行代码的**三点抛物线亚采样插值**之后，误差直接压到 `2.3°`——足够让机器人一转头就把说话人稳稳装进摄像头画面的正中央。

当然 GCC-PHAT 也不是银弹：如果环境里某个频段完全是纯白噪声、几乎没有人声能量，硬除以接近 0 的幅度会把纯噪声放大。因此工程实现通常会加一个小正则项 `eps`（防止除零），或者只在人声主频带（如 `300 Hz ~ 4000 Hz`）内做相位加权，并配合 VAD 只在人声活跃帧更新 DOA 角度。

## [ALSA] PCM、ALSA 与 XRUN：为什么视觉一卡，半个唤醒词就丢了

算法在离线脚本里跑出 2.3° 精度，搬到嵌入式 Linux 开发板上却经常出现一个诡异现象：安静的时候喊十次醒十次，一旦摄像头打开、NPU 开始跑目标检测，喊「小智同学」就频频没反应。十有八九不是模型不准，而是底层音频管线发生了 **XRUN**。

先理清这三个底层术语的关系：
- **PCM**（脉冲编码调制）：麦克风经 ADC 采样后最原始的未压缩数字音频流。端侧语音最常见的格式是 `16 kHz / 16-bit signed LE / 单声道`（或 4/6 通道交错），每 20 ms 是一拍（`320 frames`，单声道 `640 B`，4 麦 `2560 B`）。
- **ALSA**（Advanced Linux Sound Architecture）：Linux 下的标准音频子系统。声卡驱动在内核里维护一块**环形缓冲区（Ring Buffer）**，切分成若干个 `period`（比如 `4 periods × 320 frames = 1280 frames`，总容量 `80 ms`）。硬件 DMA 像水龙头一样按 `16000 Hz` 恒定往里注水，应用程序必须在缓冲区灌满之前调用 `snd_pcm_readi()` 把水舀走。
- **XRUN**（Overrun 录音溢出 / Underrun 播放欠载）：如果应用程序因为别的事情卡住、超过缓冲区总时长还没来得及读取，新采到的音频就会把没读走的旧数据冲掉，ALSA 驱动把音频流切入 `XRUN` 状态，`snd_pcm_readi()` 直接返回 `-EPIPE`。

拿 `code/verify_doa.py` 的具体数字算一笔账：环形缓冲设成 `4 × 20 ms = 80 ms`（`1280 frames`），如果在同一主循环里夹了一段耗时 `120 ms` 的视觉后处理或磁盘写日志，这 120 ms 里硬件 DMA 照常塞进来 `1920 frames`，直接超出容量 `640 frames（40 ms）`。驱动立刻报 `-EPIPE`，整段缓冲区里的语音被撕掉一块——「小智同学」变成「小…学」，KWS 根本不可能认出来。

::: interactive xrun-lab title="ALSA 环形缓冲与 XRUN：为什么必须给音频开独立线程" hint="SWITCH / INJECT STALL" note="对比单线程混跑与独立音频线程，点击「注入 120 ms 视觉卡顿」看环形缓冲与唤醒词发生了什么。"
| 线程架构 | 遭遇 120 ms 视觉/IO 卡顿时 | ALSA 环形缓冲（80 ms）状态 | 对唤醒词的影响 |
|---|---|---|---|
| 单线程混跑（视觉与音频共用循环） | 音频读取被迫停摆 120 ms | 新到 1920 frames 溢出 640 frames，触发 -EPIPE (XRUN) | 丢掉「智同」片段，唤醒词残缺漏检，不恢复还会永久停采 |
| 独立音频线程（硬隔离 + 异步事件） | 视觉线程卡顿不影响音频线程调度 | 每 20 ms 准时取走 320 frames，水位稳定在 25% | 完整保留「小智同学」，唤醒准时触发，且预留 EPIPE 自愈恢复 |
:::

防住 XRUN 的工程守则非常明确，只有三条：
1. **音频采集与 VAD/KWS 必须跑在独立线程，与视觉采集、NPU 推理、网络请求、磁盘日志零锁共享**。事件只通过无锁或极短锁的非阻塞回调/队列往外发，绝不把大块推理或阻塞写操作塞进音频读循环。
2. **明确捕获 `-EPIPE` 并做自愈恢复**。Linux 非实时内核下偶尔仍可能遭遇调度抖动或 USB 麦阵瞬时重连；读接口返回 `-EPIPE` 时不能直接退出线程，而要立刻调用 `snd_pcm_prepare()`（或清缓冲重置）拉起采集，同时记录 `xrun_recovery_count` 指标用于线上监控。
3. **合理配置 `period` 和 `buffer` 大小**。太小（如总缓冲 20 ms）一抖就 XRUN；太大（如 1 秒）唤醒延迟会飙升。工程甜点区通常是 `period = 20 ms`、`buffer = 4~8 periods (80~160 ms)`，既留出调度余量，又不拖慢 20 ms 一拍的流式喂入节奏。

```cpp
// 典型的 ALSA 独立音频读循环与 XRUN 自愈骨架（伪代码示意）
while (running_.load(std::memory_order_relaxed)) {
    const int n = audio_dev_->readFrames(pcm_buf.data(), 320);  // 20 ms @ 16 kHz
    if (n == kErrorPipeXrun) {
        ++xrun_recovery_count_;
        audio_dev_->prepareOrDrop();  // 清缓冲并重新进入 PREPARED 状态
        vad_->reset();                // 避免残缺帧污染流式隐状态
        continue;
    }
    if (n <= 0) {
        reopenWithBackoff();          // USB 麦阵热拔插退避重连
        continue;
    }
    if (vad_->isSpeech(pcm_buf.data(), n) || hangover_frames_ > 0) {
        if (kws_->feedAudio(pcm_buf.data(), n, keyword, score)) {
            float doa_deg = 0.0f;
            bool doa_ok = audio_dev_->queryHardwareDoa(doa_deg);  // 单麦返回 false，麦阵直接给角度
            emitWakeEvent(keyword, score, doa_ok, doa_deg);
        }
    }
}
```

## [ARCH] 工程落地：从单麦起步到麦阵演进的接口边界

真实做一台机器人，很少一开始就把最贵的 6 麦阵列、回声消除（AEC）芯片、端侧 ASR 全部堆齐。更稳妥的工程策略是**先把接口缝留对，硬件按阶段升级**：

- **阶段 1（单麦跑通闭环）**：直接用开发板板载单麦（如 ES8388）+ ALSA 16 kHz 单声道 + Silero VAD + Sherpa-ONNX KWS。上层音频接口提前定义好 `queryHardwareDoa(float& deg)`，单麦实现直接返回 `false`（`doa_valid = false`），系统退化为「唤醒 + 原地回应 / 上次记忆方向」。
- **阶段 2（USB 麦阵即插即用 DOA）**：换成自带 DSP 的 USB 麦克风阵列（如 4 麦/6 麦环形阵，板载完成波束成形、回声消除 AEC 与 GCC-PHAT DOA）。业务层一行不改，唤醒瞬间 `queryHardwareDoa()` 开始吐出真实水平方位角，决策层立刻切到「**DOA 先粗转对准 + 视觉精调**」的快环路径。
- **阶段 3（软硬解耦的自研阵列）**：如果需要更细的控制（比如同时追踪多人说话、结合机器人自身播放 TTS 时的参考通道做软件 AEC，防止自己播报的声音触发自己唤醒），再把多通道原始 PCM 拉进主控自己跑 GCC-PHAT / SRP-PHAT 与软件 AEC。

这里有一个极容易漏掉的坑：**播报自唤醒（缺乏 AEC）**。当机器人用扬声器大声回应你或者朗读长文本时，扬声器离麦克风只有几厘米，如果直接把带喇叭回声的麦克风信号喂给 KWS 和 DOA，机器人不仅可能被自己的声音打断，DOA 还会死死指向自己的扬声器。最简单的起步兜底是**半双工静默**（播报期间暂时屏蔽或抬高 KWS 阈值），体验更好的做法是把扬声器参考信号送进硬件/软件 **AEC**（声学回声消除），实现边说边打断（Barge-in）。

## [NOTE] 小结与取舍

::: ledger
- [+] **VAD + 离线 KWS 级联** 把 90% 以上的静音和环境噪声拦在门外，让端侧小核低功耗全天候待命，断网也能毫秒级响应关键指令。
- [+] **DOA 替代视觉盲扫** 唤醒瞬间直接拿到声源水平方位角，让机械臂或云台先转头对准再由视觉精调，大幅缩短对视延迟。
- [+] **GCC-PHAT 频域白化 + 亚采样插值** 消除低频噪声的幅度霸权并把互相关峰值拉尖，在 16 kHz / 6 cm 孔径的强混响场景下把误差从 38.9° 压到 2.3°。
- [+] **音频线程硬隔离 + XRUN 自愈** 避免视觉推理和磁盘 I/O 抢占打爆 ALSA 环形缓冲，防止半个唤醒词被无声吞掉。
- [-] **2 麦线性阵存在前后镜像模糊** 只能区分前半平面 -90° ~ +90°，需要 360° 全向定位必须上 4/6 麦环形阵。
- [-] **纯软件 DOA 不等于搞定全双工** 机器人自己发声时需要半双工门控或 AEC 回声消除，否则容易自唤醒和角度乱跳。
:::

::: lessons
1. **先切快环和慢环，再选模型。**唤醒词和声源定位属于 300 ms 级本地确定性快环，必须和云端大模型、视觉大帧处理彻底解耦。
2. **用物理尺度倒推算法必要性。**算完 6 cm 双麦在 16 kHz 下 1 个采样点等于 20.7°、80 ms 缓冲扛不住一次 120 ms 卡顿，就知道为什么需要亚采样插值和独立音频线程。
3. **先把演进接缝写进接口。**单麦阶段就让音频抽象层预留 DOA 返回位和有效标志，后续换上 USB 麦克风阵列就能零改动激活听声辨位。
4. **永远为驱动异常写自愈路径。**ALSA XRUN 和 USB 音频设备热拔插在长跑系统里一定会发生，捕获 EPIPE 重置缓冲并复位流式模型状态，比事后查为什么「喊不醒」省十倍力气。
:::
